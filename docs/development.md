# Development

Notes for anyone changing the code. If you only want to use the app, see the [README](../README.md).

## Ground rules

- UK English in the interface, comments, file names and documentation.
- Kilograms and metres only. A report in other units is refused.
- The PDF is the source of truth. The engine copies what it prints and calculates nothing.
- Never guess. Anything unreadable becomes a problem that names the array, not a made-up figure.
- No server, accounts, tracking or outside network calls.
- Real names do not go into fixtures or examples.
- Every new dependency needs a reason in the pull request.

## How reading works

pdf.js gives each piece of text with its page and position. The engine groups pieces into lines by height, then walks the lines in order. Group headings, source headings and the physical configuration section are read. The acoustic configuration section is skipped.

The enclosure table is read by column position, not by order, because some cells are blank (a sub has no angle) and values are right aligned under their headings. A page break repeats the table heading and the parser carries on.

A stacked array may print a `# fixations:` count and one line for each fixation, such as `Front right fixation position (X; Y; Z, m): Fr (-2.84; 4.6; 1)`. The parser keeps the count and, for each line, the name as printed (Fr, Fl, Rr, Rl) with X, Y and Z. Both fields are optional on an array, so an array without the lines is unchanged. The lines were seen only in sample E, on its eight KARA II stacks, always four with a Z of 1. A repeated `# fixations:` line, or the same name on two lines, raises a check; both positions are kept and the last count is used. No other wording is read: any other line that looks like a fixation is reported as not understood.

Group nesting is not printed, only a number. A group numbered 1 starts a deeper level, and a group numbered n replaces the group numbered n minus 1 at the same level. This reproduces the nesting in both samples. If the numbering ever fails to follow that rule, the parser reports a problem and the group names may be wrong.

## Checks on what was read

Two levels of problem come back with the report.

An error means the figures cannot be relied on: no text, not a Soundvision report, or units other than kilograms and metres.

A check means something looks wrong and should be compared with the PDF: a line the parser did not understand, an unreadable cell, a motor count that does not match the pickups, enclosures out of order, or a fixation count that does not match the fixation positions found. A flown or stacked array with no Position line is also flagged. For flown arrays the parser compares figures the PDF prints against each other. Each site angle should equal the one above minus its angle, and the first and last site angles should match the top and bottom site. Every row except the first needs an angle, unless its site is the same as the one above (a rigid SB18 block in a hang prints no angle), and where the type changes and the site does not move the angle is not subtracted, as an SB18 block above KARA II is printed. A table that has lost its Angle column gets one check about the column. Heights are not compared, because with large splays the front edges of enclosures do not meet. Stacked arrays follow different rules, so only their numbering is checked. A stack laid out in columns is numbered from #1 in each column, and the column numbers must run C1, C2, C3 with none missing and no plain rows mixed in. A ground stack can be laid out in columns, labelled `C1 #1`, or in rows, labelled `R2 #1` and `R1 #1`. The parser keeps each label as printed, in the `column` or the `row` of the enclosure, and checks that the numbers inside each column or row run from `#1` in order, that the columns or rows are numbered from 1 with none missing, and that labelled and plain rows, or columns and rows, are not mixed.

## Tests

Expected values in `src/engine/parse.test.ts` were read by hand from the sample PDFs. Do not edit an expected value to make a test pass. Raise it instead.

The property tests draw 300 random reports in the Soundvision layout, with page breaks in random places, and require that they read back exactly with no problems. Other tests cover empty and non-report PDFs, pounds and feet, unreadable cells, unknown lines, shuffled input and garbage.

The two sample PDFs carry real venue and author names, so they are listed in `.gitignore`. The committed fixtures replace those names. When the PDFs are present in `reference/`, extra tests check that pdf.js still produces exactly the committed fixtures. Without them those tests skip, which is what happens in CI.

## Panflex label

A fly sheet shows a label next to each enclosure: 70, 110, or 90 with On or Off. `panflexLabel` in `src/engine/panflex.ts` produces it. It is the one value the engine derives, so the rule is written out there and tested against the owner's sample output.

The two Panflex figures are added together. When they differ, the wider side is On if it points towards the stage centre and Off if it points away, seen from the box. In the samples the first figure points towards negative X and the second towards positive X, so the answer depends on which side of X = 0 the array sits. Left-hand arrays match the sample output. Right-hand arrays follow by mirroring and are not yet checked against a reference.

## Inputs on top of the report

The PDF does not hold the show name, venue, system engineer, company, Z-axis zero or a ground offset, so the interface asks for them. The offset can be set for every array and overridden per array. Heights on the sheet are the report's heights minus the offset, rounded to 0.01 m. An array's Position Z is its top height and its Bottom elevation is its bottom height. If an offset is not a number, the heights are hidden and the field says why. Nothing is ever shown as 0 because it was missing.

## Mirrored arrays

When two arrays are exact left-right copies, the fly sheet shows the first one and names the other on its card. `findMirrors` in `src/engine/symmetry.ts` decides. The test is strict: group, configuration, bumper, motors, weights, heights, sites, every enclosure row and every warning must match. X and azimuth must be negated, pickup X must be negated, and the two Panflex figures must be swapped. A difference of 0.01 in any figure means no pairing. An array on the centre line is never paired. Azimuths pair when they add up to 0 modulo 360 (within 1e-9), so 180 and 180 pair, and so do 180 and -180. In the group names a leading `YZ Sym of ` or `XZ Sym of `, repeated if need be, is ignored on each side (`sameGroups`), for both left-right and front-back pairs, and each card keeps its own names. A difference in configuration text still means no pairing. Only the report decides, so nothing the person typed (title, note, ground offset, patch, carts) splits a pair.

Mirrors can also run front to back. `isMirror(a, b, 'frontBack')` negates Y instead of X, requires the two azimuths to add up to 180 modulo 360 (within 1e-9), and keeps X, Z, every site angle and every enclosure row the same. It is stricter on purpose. It never pairs an array whose Y is 0, an array that has fixations, or two arrays whose Panflex figures differ on any row, because nobody has yet seen how the report names the fixations or the Panflex sides of such a pair. `findMirrors` makes two passes, left-right first over every array and then front-back over the arrays still free, so each array is in at most one pair and a report with only left-right mirrors gives the pairs it always did. Samples A and B give the same pairs as before. Sample E also gives two front-back pairs, the two centre hangs with azimuth 0 and 180 and the subs KS28 1 and KS28 2, and a test records them. The wording on a card is the same for both kinds.

Fixations are part of the strict test: a pair needs the same count, and the fixations of one array, with the side letters swapped (Fr with Fl, Rr with Rl) and X negated, must equal those of the other as sorted lists, so a repeated name is matched one to one.

A card that stands for a pair carries one small plain line under the title, `Also mirrored with: ` and the name of the other array, with no box so it cannot be mistaken for a warning. It is the same on screen, on the printed pocket card, in the PDF and in the image (`mirrorNote` in `card-content.ts`). A line above the cards, with a Show them button, and a tick in Settings show the mirrored arrays as well. Pairing ignores everything typed, so a pair still collapses when the two arrays have different titles, notes, offsets, patches or carts. The shown card prints its own title, note, patch and carts, and the hidden partner's stay in the file and are not printed, with no notice. With the mirrors shown each card shows its own. The shown card uses its own typed ground offset, else the one typed on its partner (`effectiveOffset` with the mirror index), else the one for every array; the partner's offset never overrides a typed own one. The rigging summary lists every pickup and every fixation position of the arrays chosen for printing and of the mirrors their cards stand for, because mirrored arrays hang from different points and stand on different ones. The one on screen lists every array.

## Saved files

A saved file is JSON in the format `arraysheet/16`. It holds the report as read from the PDF (not the PDF), the problems found, the show details, one ground offset, print choice, card title, note, deleted choice, pair of pickup symbols, pair of additional weights, cable patch, carts and rigging plot choice per array, whether the plot prints, whether it shows the Position dots and the outlines, the table of cart sizes, the value written for each of the four plot symbols, the venue underlay (or null), the status, the revision, the name of the PDF and the time it was saved. The schema is `src/schema/array-file.ts`.

Every opened file is treated as untrusted. In order, it must pass the size limit (8 MB), parse as JSON, say it is an `arraysheet` file, be no newer than this version, and pass the schema. The schema also caps the number of arrays, enclosures, pickups (8), fixations (16) and warnings, and the length of text, a fixation name included. Anything wrong stops the open with a plain-English message that names the field. Nothing is partly opened.

Each version has a migration to the next in `src/files/migrations.ts`. There are fifteen steps so far. Version 2 added the print choices, so the first step turns a version 1 file into version 2 by choosing every array for printing, which is what a version 1 file did. Version 3 added the venue, so the second step gives a version 2 file an empty venue. Version 4 added the optional column of an enclosure row, and version 5 added the optional fixations of an array. Neither changes an older file, so the steps from 3 and from 4 only change the format number. Their purpose is to make older copies of the app refuse a file that may hold columns or fixations, because they would drop them without saying so. Version 6 added the origin note (P0) that the rigging plot prints, so the last step gives an older file a blank one and turns the side labels on; an older copy of the app would drop the note, so it refuses version 6 files. Version 7 added a card title and a note for each array, the list of deleted arrays, and the notes and the date of the show; the last step gives every array a blank title and note, gives the job blank notes and a blank date, and keeps all the rest. An older copy would drop the titles and notes and bring deleted arrays back, so it refuses version 7 files. Version 8 added the plot symbol of each pickup, a front and a rear choice per array; the last step gives every array the 1 ton circle, which is what the plot drew before. An older copy would drop the choices when it saved, so it refuses version 8 files. Version 9 added the venue underlay of the rigging plot; the last step gives every older file none, and an older copy would drop it, so it refuses version 9 files. Version 10 added the cable patch, a feeder and a way for each enclosure row of each array; the last step gives every array one blank pair for each of its enclosures, and an older copy would drop the patch when it saved, so it refuses version 10 files. Version 11 added the carts: a table of the boxes per cart for each type of enclosure, and for each array whether its carts were cut by hand and where. The last step gives every older file the usual sizes (K2 4, KARA II 3, KARA 3) and every array automatic, and an older copy would drop the sizes and the hand cut carts when it saved, so it refuses version 11 files. Version 12 added the optional row of an enclosure row, for a ground stack laid out in rows (`R2 #1`, as the label of the report). Nothing in an older file changes; the last step only moves the version on, so an older copy refuses a version 12 file and cannot open one with rows and drop them. Version 13 added the choice of which arrays are on the rigging plot (`plot`, one true or false per array) and whether the plot prints (`print_plot`). The last step puts every array on the plot and turns printing on, which is what the plot did before, and an older copy would drop the choices when it saved, so an older copy refuses version 13 files. Version 14 moved the value written for a plot symbol (such as `1 t`) from the single pickup to Settings: one value for each of the four shapes for the whole job (`symbol_values`). The last step gives every older file the usual values, and drops the text that a version 13 file could hold on a single pickup, so that text is lost; the pickups keep their shapes. An older copy would drop the values when it saved, so it refuses version 14 files. Version 15 added the choices to show the Position dots and the array outlines on the rigging plot (`show_position` and `show_outlines`). The last step turns both on, which is what the plot did before, and an older copy would drop the choices when it saved, so an older copy refuses version 15 files. Version 16 added the additional weight of a pickup (`extra_weight`, one front and rear pair of text weights for each array). The last step gives every array a blank pair, and an older copy would drop the weights when it saved, so it refuses version 16 files. A file from a newer version is refused, not opened and silently trimmed.

Because the file holds the report as read, it reopens exactly as saved, whatever the PDF reader does later.

## Status, revision and the lock

Status is Draft, Issued, Approved or Superseded. The revision is blank for the first issue, then A, B, C, through Z, then AA. `nextRevision` does the counting.

A file opened as approved or superseded is read-only, and so is a file that has just been saved as one. Choosing Approved on a draft does not lock it, so it can still be saved. Create new revision starts a draft with the next letter and no file name, so it saves under a new name such as `Main stage - Rev B.arraysheet.json`. The old file is never changed. Setting the old one to Superseded is left to the person.

## Update from PDF

With a file open, Update from PDF reads a newer PDF and compares it with the saved report (`src/engine/compare.ts`). Arrays are matched by name. The comparison lists every difference in the arrays, the enclosure rows, the pickups, the weights and the warnings, plus the Soundvision version, date and project name. If nothing differs, the app says so. If something does, the person chooses Update from new PDF or Keep as saved. A PDF that reads with an error is refused and the file stays as it was. After an update, ground offsets, print choices, titles and notes stay with the array of the same name (`updatedDoc` in `src/files/doc.ts`), plot symbols follow `trackMarkers`, cable patches follow `trackPatches`, hand cut carts follow `trackCarts` (kept while the array of the same name has the same enclosures in the same order, otherwise back to automatic and listed), the table of cart sizes, the venue underlay and the show details are untouched, and the file counts as having unsaved changes. A deleted array that is in the new PDF comes back with the new data, because `deleted` is cleared and the comparison lists it once as restored instead of figure by figure, with its cable patch kept; one that is not in the new PDF is dropped with its choices.

## Titles and notes

`titles` and `notes` are lists in the file with one entry per array, by position in the report, like `offsets`. A blank title means the report name. `displayName` gives the name shown, and `sheetModel` puts it into `sources`, so every output uses it. `SheetEntry` keeps the report name (`reportName`), whether it is renamed, and the note. `cardContent` turns those into `reportNameNote` (`Soundvision name: <name>`, only when renamed) and `note`. Update from PDF matches by report name, so a title and a note stay with the array. The compare dialog names a renamed array as `<report name> (shown as <title>)`.

The note is drawn by `noteLines` in `array-image.ts` for the PDF and the image, and as a `pc-note` paragraph in the print view, which keeps line breaks with `white-space: pre-line`. The bold word Note runs into the first line. The note is plain text, up to 300 characters, and a title is one line of up to 60. The file refuses control characters, and the boxes drop them as they are typed.

## Deleting arrays

Delete sets `deleted[i]` and leaves `report.sources` as read. Everything else is stored by position in the report (offsets, print choices, titles, notes), so removing an entry would shift them all, and the file would no longer be the report as read. Nothing is added to the file by a delete, so repeated deleting and restoring does not grow it. `sheetModel` is the one place that reads the arrays: it returns `sources` (all arrays at the same positions, each with the title shown in place of its name), `live` (the positions not deleted) and `deletedList`. Cards, printing, the PDF, the plot, the DXF and the rigging tables read those, never the report directly, and `deleted-output.test.ts` checks that a deleted or renamed array's old name appears in none of them. Mirror pairing runs over the live arrays only (`findMirrors(sources, skip)`). A pair collapses on the report figures alone, so a note on the array that is not shown prints only when the mirrors are shown too.

Undo is a stack of positions kept by `App` for the session. It is never saved and is cleared on open, new, Update from PDF and Restore, while the deleted choices themselves are saved, so a reopened file offers Restore but not Undo. A read-only file cannot delete, undo or restore. `visibleProblems` hides the checks that name only deleted arrays, in the problems panel and in the page count of checks; errors always stay.

## Three layers of saving

1. Every browser: a file input to open and a download to save.
2. Chrome and Edge on a computer, found by feature and never by browser name: the File System Access API. `src/files/fs-access.ts` holds the pickers, `src/files/save-flow.ts` decides what Save and Save As do, and `src/files/recent.ts` keeps file handles in IndexedDB for the Recent list. Permission is asked for again when a file is reused.
3. Autosave to IndexedDB, described below.

`saveText` takes a request and returns what happened: cancelled, denied, saved to a handle, or downloaded. Save writes back to the handle when there is one and asks where when there is not. Save As always asks. Nothing is reported as saved unless the write succeeded. Anything typed while a picker was open stays unsaved, because only the text that was written counts as saved. Create new revision forgets the handle, so Save asks where and the original file is never touched.

The Playwright tests cannot drive a native picker, so they replace the two picker functions with ones that return real handles from the browser's private file system. Everything after the picker is the real code.

## Install, offline and updates

`vite-plugin-pwa` builds the manifest and precaches the app with Workbox, using a custom service worker in `src/sw.ts` (strategy `injectManifest`). The precache includes the PDF reader's worker, so a PDF opens with no network. The icons in `public/` are rendered from `favicon.svg` by `npm run icons` and committed, so builds need no browser.

The service worker waits. A new version is used only after the person presses Reload in the update prompt (`src/ui/UpdatePrompt.tsx`), and the prompt mentions that unsaved changes are kept by autosave. The app checks for a new version every hour while it is open.

## File handler and share target

The manifest registers the app as a handler for `.json` files, so a saved file opens on double-click in the installed app (Chrome and Edge on a computer). It does not register for PDFs, because the app should not take over every PDF on the computer. `src/files/launch.ts` receives the file through `launchQueue`.

The manifest also declares a share target. On Android a saved file or a Soundvision PDF can be shared into the app. The service worker receives the POST, keeps the file in a cache, and sends the app to `?shared=1`, where `src/files/share-target.ts` takes it out and opens it. Playwright tests simulate the Android POST with `fetch`, because the app's strict CSP blocks form submissions.

## Autosave

While there are unsaved changes, a copy is written to IndexedDB (through idb-keyval) about a second after each edit. On the next visit the app offers to restore it. The offer says it is a safety net and not a save. The copy is checked like any opened file, and one that fails is thrown away. Saving, starting again, opening another file or declining the offer removes it. If the browser refuses IndexedDB (a private window, or no room for a big venue), saving to a file still works, and the header says so, next to the unsaved changes note, so nobody relies on a copy that was not kept.

The `beforeunload` warning also fires while there are unsaved changes.

## Printing

`src/print/PrintSheet.tsx` renders the whole printed sheet off-screen at all times, so it can be measured, and `print.css` shows it only when printing. The editing screen is hidden in print. A draft is marked with DRAFT on every pocket panel, because a word across the whole A4 page would be cut up by the folds. The rigging page carries one.

Every card is laid out at a fixed width (half the page less padding), and its height comes from `layoutPocketCard` in `src/print/pdf-layout.ts`, the same function the PDF uses. The print view feeds it text widths measured on a canvas in the page font, and the PDF feeds it the widths of Helvetica, which match Arial. `planPages` in `src/print/layout.ts` then sorts them. A card no taller than a pocket panel (`CELL_H_MM`, 119.5 mm) stays in the panel at full size, four to a grid page. Any taller card goes in a long column (`LONG_H_MM`, 261.5 mm), two to a long page, and shrinks to fit down to 50%. A card that still does not fit at 50% has a long page to itself and is allowed to run on rather than be cut off. Long pages come first, then grid pages, each kind in report order, and the rigging summary page always comes last. The fold between two long columns is a single dashed vertical line at the 99 mm centre, drawn in the same dash, weight and grey as the grid page folds. In the print view it is the `::after` of `.as-long`, positioned absolutely so the columns keep their width and height; in the PDF it is `dashedCentre`. It is drawn even when the page holds one column.

Each pickup row of the rigging tables also carries `edge`, from `edgeDistances` in `src/engine/plot.ts`: how far the pickup lies from the front and rear edge of the array's box, along the array axis, in metres to 2 decimals, positive inside the box and negative outside. A front pickup carries only the front figure and a rear pickup only the rear one, unless the array has a single pickup, which carries both. `edge` is null when the report lacks a Position, size or azimuth, and the table shows the dash; a blank cell means the figure does not apply to that pickup. The screen table, the print view and the PDF share `edgeText` and the same column widths, and `riggingEdgeNote` explains the columns under the tables. `plotArrays` draws every array except those missing a Position, size or azimuth: only an array marked stacked is a stack, and any other, including one with no mounting stated, is drawn like an array with no pickup or with pickups.

The rigging page has a pickup table (`riggingRows`) and, when any printed array states fixations, a second table (`riggingFixations`) with the Z as the report prints it. `riggingNote` words the line under them so it names only what is listed. Both tables use fixed column widths from `pdf-layout.ts` and one line per row. `clipRiggingCell` cuts the middle out of a name that does not fit its column and keeps both ends, by the same rule in both tables, in the print view and the PDF. The fixation table gives the Array column 80 mm so the report's own derived names fit. `riggingSubtitle` builds the line under the heading (show, venue, Z-axis zero) for the print view and the PDF alike. The print stylesheet sets the row line height to 1.2 so a rigging row is the height the PDF draws. The pickup table keeps 8 pt text. The fixation table is the long one, so its rows follow the pocket card: 7 pt text in a row 10.5 pt (14.0625 CSS pixels) high, drawn by `layoutRiggingPage` and set in `print.css` (`.as-table-second`). With report E (12 pickups and 32 fixations) the page then needs about 1010 CSS pixels where 986 are free, so it is scaled to 0.975 and does not overflow. That leaves the fixation text at about 6.8 pt, the pickup text at about 7.8 pt, and the small print and the QR caption at about 6.3 pt and 5.4 pt. With the earlier 13 pt rows the scale was about 0.88. A unit test holds the PDF scale and an e2e test checks the print view row heights and scale. If a report ever needs the page scaled below about 0.9, the option is a second page for the fixations.

The job carries two more fields from format 7. `job.notes` is a note for the whole show, 500 characters at most, with line breaks kept and other control characters refused; `riggingNotes` in `pdf-layout.ts` trims it, and the print view, the PDF and the on-screen summary print it as a Notes paragraph under the rigging subtitle, and nowhere else. The PDF wraps it with `noteLines` and the print view with `white-space: pre-line`; the print view measures the page, so the scale follows either way. With no notes nothing is drawn and the page does not change. `job.showDate` is YYYY-MM-DD text from a date input, checked by `isShowDate` in `src/files/show-date.ts` (a real calendar date or blank, refused otherwise) and printed by `showDateText` as 23/10/2026. It goes first in the pocket panel's details line, after the venue in the card context line used by the PNG export, and after the venue in the rigging subtitle, which the plot page reuses. It is not the report's own Date line.

The rigging summary panel on screen (`RiggingSummary`) shows the same two tables and the same `riggingNote` line as the print, with every array listed and no name cut, because the screen always shows every array. The print and the PDF list only the arrays chosen for printing, plus the mirrors their cards stand for.

Only the rigging page is still measured in the browser. While printing, its measuring copy is hidden, so a measurement then would read zero. The measuring code ignores a hidden container and keeps the height it already has. A Playwright test covers this.

Each pocket panel has a header (`panelHeader` in `src/print/panel-header.ts`) and a footer of its own, because folded to A6 it is all you hold. The header has the show and venue (or the Soundvision project if none was typed), the status, and the details that are filled in: show date, project, engineer, company and Z-axis zero. The panel footer is the footer text plus a credit line (`CREDIT_TEXT` in `footer.ts`), which the card image and the plot page carry too. A card with one pickup shows it in a Frame/Bar Hole row (`pickupFact`). Grid and long pages therefore have no page footer. Only the rigging page keeps one. The page planner takes the header and footer out of the height a card may use.

The footer is `printFooter`. It says which version, which Soundvision report, which file and when. A file that has changed since it was saved is marked. The last page carries the small print from `src/print/small-print.ts`. It is the approved wording of `DISCLAIMER.md`, and a test fails if the two differ by a word. Change them together, and only with the owner's approval.

The Playwright PDF tests check three things: the number of PDF pages, that every card sits inside its panel and every footer inside its page, and that the text is what the screen shows. PDF output is a Chromium feature, so those run on Chromium only.

## The rigging plot

The plot is a plan view of the arrays the person has on the plot (`SheetModel.plottedSources`, see Plot choices below), drawn on a landscape A4 area and turned a quarter turn anticlockwise onto the portrait sheet, so it reads when the sheet is turned clockwise. It sits after the card pages and before the rigging summary, and a table longer than 24 points continues on further pages. A report with no drawable array, or none on the plot, has no plot page.

`src/engine/plot.ts` holds the geometry. `footprint` puts the middle of the front edge at Position and runs the box rearward by the depth, turned by the azimuth read as a compass bearing, clockwise from +Y. In samples A, C and E every pickup lies on the centre line of its box to within 0.02 m, and the front pickup lies forward of the rear one along the array axis; a test locks both. That shows the azimuth direction agrees with the report's own figures, but the distance of the front pickup from the front edge is not yet checked against a real hung array. `numberPickups` numbers the pickups: arrays are grouped in rows by Position Y, highest first, a row being arrays within 1 m of the first one in it; inside a row the highest X comes first; a front pickup comes before the rear one of its array. An array with no Position, spatial dimensions or azimuth is left off and named under the plot. A stacked array uses the same footprint and carries no pickups, so it is not numbered; in sample E the fixation positions of every stack lie on the front and rear edges of its box, and a test locks that, which confirms Position is the front edge for stacks too.

`src/print/plot-layout.ts` is one pure function, `layoutPlotPages`, that returns drawing steps in millimetres (lines, circles and text with colour roles). `PlotSvg.tsx` draws them for the print view (rotated) and the on-screen preview, and `plot-pdf.ts` draws them with pdf-lib, so the three agree. The screen palette has red and green axes and a red Position dot; the print palette is black and grey. The scale is the largest standard ratio (1:50 to 1:2500) at which everything, the origin included, fits. A pickup symbol is 250 mm across at scale but never under 2 mm on paper. The Position dot is 0.55 mm in radius at 1:150 and shrinks with the scale to a floor of 0.3 mm (`dotRadiusMm`). A stack is a solid box with crossed corners (`stackBox`). Its Position is the same filled dot as any other array, in the plot and in the DXF, and the key has one Position entry. The plot shows no heights: array labels are the name, the stated total weight and the spacing (an array with no pickups carries its name alone), and pickup labels are the number and the motor load, so the ground offset plays no part in it. The one figure the plot works out is the spacing between an array's front and rear pickups, `planSpacing` in `src/engine/plot.ts`, the distance on the plan from X and Y only, rounded to 2 decimals. It is the last line of the array label, under the name and the Total line (each left out when there is nothing to show), and it is in the Spacing column on the front row. The line between the pickups carries no text. Array labels are placed in the best of nine fixed orders and six seeded shuffles, tried on copies, so the same report always gives the same drawing. Labels try the right of the marker first, then left, above and below, then further out with a thin leader line. The small print is `PLOT_SMALL_PRINT` in `small-print.ts`, locked by a test.

Known label clashes: labels keep clear of lines, markers, boxes and each other, but placement is greedy. In sample C, at 1:400, the six KS28 and four KARA II stacks stand in pairs a few millimetres from the origin lines, so several leaders there cross an origin line or a neighbour's label, and a test allows up to ten such leaders on C. Samples A and E have none, and a new clash on either fails a test.

`src/print/plot-dxf.ts` writes the plot as an R12 style ASCII DXF, with no library. Geometry comes from the engine at full size: millimetres, the report's X and Y times 1000, origin at 0,0, so the file does not depend on the plot scale. The labels, leaders and axis text come from `PlotPage.plan`, which `layoutPlotPages` fills on the first page with where it placed each line of text and each leader in paper millimetres, plus the paper millimetres per metre and the origin. The writer converts those back to real millimetres and sizes the text by the plot ratio, so the labels clash as little as on the page. Marker symbols are 250 mm across, not the paper minimum. Layers carry the line types (dashed, dash dot) and the header sets `$INSUNITS` 4 and `$MEASUREMENT` 1. Characters outside ASCII are written as `\U+XXXX`. The tests read the file back with a strict structural parser, because no DXF library is installed.

Pickup symbols live in `src/engine/markers.ts`: four shapes (`two`, `one`, `half`, `quarter`), the value written for each (`SymbolValues`, starting at 2 t, 1 t, 0.5 t and 0.25 t, at most 12 characters, a blank one falling back to the usual value through `symbolValue`), and `markerPrims`, the strokes of each shape centred on the pickup. The plot layout and the DXF writer both draw from those strokes, so the shapes agree everywhere. Every shape can always be picked, and the weight of the array is never checked. A symbol is always black. The values are job level: `Doc.symbolValues`, edited in the Symbols part of Settings (`SymbolRow` in `SettingsDialog.tsx`, with the shape drawn by `SymbolIcon`), saved as `symbol_values`, kept by Update from PDF and fixed on a read-only file. They show in the plot table's Symbol column, the key, the picker on each card and, as one line of notes, in the DXF, which has no label for single pickups. The choice is a `MarkerPair` per array, front and rear, in `Doc.markers` and the `markers` list of the file; the default is the 1 ton circle. A read-only file keeps a choice in `Doc.markerOverride` for the session only, like the print choice, and Create new revision makes it real. A collapsed mirror image takes the symbols of the card that stands for it (`plotContent`). Update from PDF follows a symbol with `trackMarkers`: it stays when the array of the same name still has the same pickup, the front or rear one with the same position number, and otherwise goes back to the default and is listed in the comparison.

## Carts and Settings

`src/engine/carts.ts` holds the carts. A break at index `b` means a new cart starts at row `b`, counted from 0 in report order. `forcedBreaks` finds the breaks no one can remove: where the type, ignoring surrounding spaces, changes, or where the stack column does. `autoBreaks` cuts each run of one type in one column with the size for that type (`sizeFor` matches the type after trimming, ignoring case, so `KARA II` and `KARA` are separate rows): a run no longer than its size, or a type with no size, is left whole; a flown array, or one whose mounting is not stated, is cut from the top so the short cart is last; a stack is cut from the bottom so the short cart is first. `normaliseBreaks` makes any list safe (whole numbers inside the table, the forced ones added, sorted, once each), `toggleBreak` never removes a forced break, `groupsOf` gives the sizes (`[4, 4, 3, 3]`) and `cartShade` marks every other group from the top, the first white. A test holds a table of cases, including a mixed array, a stack, a stack in columns and an uncut type. The row of a stack laid out in rows does not force a break, only a change of type or of column does.

An automatic array stores nothing and is cut again from the sizes every time, so a change of sizes reaches every automatic card. A hand cut array stores its own list in `Doc.carts` (a key present means by hand). In the file, `carts` has one entry per array, `{ manual, breaks }`, and `cart_sizes` is the table. The schema refuses sizes that are not whole numbers from 1 to 24, a blank, repeated (ignoring case) or control character type, more than 100 sizes, breaks outside the table or not strictly rising, and breaks on an automatic array. A read-only file cannot change either; there is no session override, because an approved file must print what it says.

Shading is one flag per row in `CardContent.cartShade`, which the print view (`pc-cart` on every cell outside the Feeder and Way columns), the PDF (one `rect` of `#ebebeb` from the left edge to the first patch column, drawn before the row's text) and the PNG read, so row heights and page planning do not change. `#ebebeb` is neutral grey with printer luma 235, 20 below white and 7 above the header grey `#e4e4e4`; black text on it is 17.6 to 1. On screen the same flag bands the row with `--band` (`#e8ebf0` Day, `#262b34` Night), a solid line starts each cart (`cart-start`), and each gap has a real button (`cart-break`, `aria-pressed`), always visible, never hover only. Where the type changes the gap has a fixed marker instead of a button.

A collapsed mirror pair shows the carts of the array it shows. The `hidden` entries of the sheet model carry only the name and the array they hide behind. Nothing tells the person that the partner's carts differ, and pairing does not look at carts.

`src/ui/SettingsDialog.tsx` is the Settings box, on the same `Dialog` as the other pop-ups (the browser's own `dialog`, so focus stays inside and Escape closes it). It holds the table of cart sizes (one field for each type in the live arrays in report order, then saved types the report does not have, marked as such), the side labels tick, the four symbol values, and the tick that shows the mirrored arrays. The Origin (P0) note, the ground offset every array uses and a Venue button sit in the `plot-controls` row under the plot preview (`RiggingPlotPreview`), with Print rigging plot and Download DXF. The Venue button opens `src/ui/VenueDialog.tsx`, which wraps `VenuePanel` (import, replace, remove, the summary messages and the layer ticks) in the same `Dialog`; its label comes from `venueButtonLabel` and reads Venue, or Venue: n of m layers on. It opens in a read-only file with every change switched off; the row wraps on a phone and is always shown, so the two fields can be typed before any array is on the plot. They keep their saved behaviour, labels, validation messages and read-only state. The fly sheet heading has a line with a Show them or Hide them button that does the same as the tick. The Include venue in the DXF tick stays beside Download DXF.

## The venue underlay

`src/engine/underlay.ts` reads the text SU4SV writes and keeps a plan of it. The file has comment lines that start `"; ` (the length unit must be `m`, and a file with no unit is refused), then blocks that start `"Label","<name>"` and list x, y, z points, ended by `";"`. The layer is the label without its trailing number (`Wall 01`, `Wall_002` and `Wall` all give `Wall`; the number must follow a space or an underscore). A block of two points is one line, three or more is a closed outline, and a block of fewer than two points is skipped. Lines are rounded to whole centimetres, a line shorter than a centimetre is dropped, and a line seen twice, also the other way round, is kept once in each layer at the lowest height it has, so a wall seen from above is one line at the floor. Lines that do not parse are counted and mentioned, not fatal.

The height of a line is the average of its ends. The steps run from darkest to lightest over four equal parts of the range between the 2nd and the 98th percentile of all heights, so a few very tall things do not flatten the shading. A model with no spread in height is all in the darkest step. The limits are 60,000 lines after duplicates are removed (a roofed arena measured about 2,750), 300 layers and an 8 MB file. Over the limit the import is refused with a message that says to simplify the model in SketchUp.

In the saved file the venue is `underlay`: layers with a name, a hidden flag, and per layer a list of shades, each a step from 0 to 3 and its lines as one packed string. A line that starts where the last one ended is written as its vector, any other with a jump from the end of the last, in base 36 whole centimetres, so a line takes about ten characters and the largest real model saves in about 250 KB. A list of numbers would have taken a line for each in the pretty printed file. The schema unpacks every string to check it and counts the lines against the limit.

`layoutPlotPages` takes the layers that are on as `venue` and draws them first, before the grid, as one `segs` step for each shade, cut to the plot frame with Liang-Barsky before any step is made, so a venue much bigger than the plot costs little. `extent`, which decides the scale, never sees the venue, and a test shows the page is identical with a huge venue apart from the added steps. The venue is not an obstacle for labels. The SVG draws a step as one path, and the PDF draws each line. The DXF writer adds every line of the shown layers at full size when asked, on layers named `VENUE_` and the layer name made safe (letters, digits, underscore, at most 31 characters, kept different), with the grey of the step as the colour of each line.

## Choosing what to print

Plot choices. Each array has an Include on rigging plot checkbox, saved as one true or false per array (`plot`), on to begin with. It is independent of Print this array: `sheetModel` builds `plottedSources` from the cards the same way it builds `printedSources`, so a card that stands for a mirror image carries its partner on or off with it, and a deleted array is never in it. `plotArrays` draws only those, so an array that is off is not drawn, not numbered, not in the table, the key or the label placement, not in the DXF, and not named in the not-drawn note, which is only for arrays that lack a position, a size or an azimuth. The scale and the extent come from the arrays that are on the plot and the origin. `SheetModel.hasPlot` says whether any array is on it. Show position and Show outlines are two more view choices, saved as `show_position` and `show_outlines` and kept in `Doc.plotShow`. They only decide which steps `layoutPlotPages` emits: with Show position off the Position dots and the Position entry of the key are not drawn, and with Show outlines off the array boxes, the stack corner lines and their key entries are not drawn. The layout is otherwise the same, so the scale, the extent and the place of every label and pickup stay where they were, and the dots and boxes still count as obstacles for the labels. The DXF leaves out the POSITIONS circles and the array lines in the same way and keeps its layer table. Print rigging plot is one more flag (`print_plot`, off by choice) and `SheetModel.printsPlot` is `hasPlot` and the choice together. `plotForPrint` uses it, so the print view, the PDF and the page count agree and the footer's Page n of N has no gap; the preview and the DXF use `plotContent`, so they stay when printing is off. On an approved or superseded file the choices are kept for the session in `plotOverride`, `plotPrintOverride` and `plotShowOverride`, like the print choice, and are never saved; Create new revision makes them real.

Additional weight. `src/engine/extra-weight.ts` holds the rules. A weight is typed text, blank or at most 6 whole digits and 2 decimals, not above 100000 kg; `parseExtra` reads it, `isTypingExtra` filters what can be typed, and the file stores it plainly (`canonicalExtra`), so `12.50` is saved as `12.5`. It is content like a note, so `withExtra` does nothing on a read-only file. `extraKgFor` in `sheet-model.ts` gives the weight of a pickup, and a mirror image that a card stands for takes the weight of that card, as it takes its symbol. All sums are made in whole hundredths of a kilogram (`sumKg`, `addKg`), so no figure prints with a tail such as 589.8000001. `plotContent` adds the weight to a pickup's load and to its array's stated total, sets `additionalWeight`, and the small print then ends with `PLOT_EXTRA_WEIGHT_SENTENCE` (the approved `PLOT_SMALL_PRINT` is never edited); the DXF notes carry the same sentence. A pickup whose load the report does not state stays without one. On the rigging summary the pickup table is unchanged: `riggingRows` carries the weight as `extra`, `extraTableRows` lists the pickups of arrays that have a weight (report load, weight, total), and `riggingWeights` with `weightTableRows` gives each array with a pickup its stated total weight as its own item, plus the typed sum and the pickup loads plus that sum when any weight is used. The screen, the print view and the PDF all build those rows from the same functions. Update from PDF follows a weight with `trackExtras`, by array name and pickup position, like a plot symbol.

Each array has a Print this array checkbox. The choices are saved in the file as one true or false per array (`print`). Unticked arrays leave the print sheet and the image export, and the rigging page lists only the pickups and fixations of the printed arrays. A card that stands for a mirror image carries that mirror's pickups and fixations with it. With the mirrored arrays shown, each array is chosen on its own. The screen always shows every array.

An approved or superseded file cannot change, but it can still be printed in part. Its choices are held for the session only (`printOverride` in `src/files/doc.ts`), are never saved and do not count as a change. Create new revision starts from the choices in force. Update from PDF keeps a choice with the array of the same name. Print is off while no array is ticked.

## The one-click PDF

Download PDF builds the same sheet as the print view without opening the print window. `src/print/pdf-layout.ts` lays out one pocket card and the rigging page as drawing steps in points, and is pure, so it has ordinary unit tests. `src/print/pdf-export.ts` draws those steps with `pdf-lib` on A4 pages: long pages first (one or two full-height panels with a dashed centre fold line), then four panels to a page with dashed fold lines, a header and footer on every panel, a DRAFT word on every panel of a draft, and the rigging page with the QR code and the small print last. The page planner (`planPages`) and the card height (`layoutPocketCard`) are the same ones the print view uses, so both outputs plan every array from the same number. The only input that differs is the text width, which is measured on a canvas in the browser and read from Helvetica in the PDF. Those two agree for ordinary text, but a line that wraps differently in the two could still move a card by one line, and an array that lands within one line of the 119.5 mm limit could in principle be placed differently. The tests do not find such a case in the sample reports.

Text uses the PDF's built-in Helvetica, so nothing is fetched or embedded. Helvetica holds Western European characters only. Anything else, such as Greek or Japanese in a show name, is replaced with a question mark so the file can still be made.

`pdf-lib` is MIT licensed and has no network code. It is loaded only when the button is pressed, so it adds nothing to the first load. The tests build the PDF and read it back with the app's own PDF reader.

## Card size

A pocket panel has 119.5 mm for a card once its padding, header and footer are taken out. That holds 20 enclosure rows for a card that also has a mirror note and a motor load line, and a card without a mirror note has room for one or two rows more. Long warnings, extra motor lines, a long frame name that wraps onto a second line and a long title or group each take a line and can cost a row or two. Pocket cards always print at full size. A taller card goes in a long column with 261.5 mm, which holds about 54 rows at full size. The half-size limit of 50% is a backstop that holds about 120 rows, and no real array comes near it.

The card height in `pdf-layout.ts` reproduces the print stylesheet as Chromium lays it out: a fact row and a table row are each 14.0625 CSS pixels, a border of 0.25 or 0.4 mm is one pixel, and the title line height is 1.15. An end-to-end test measures the table rows and compares the height of every rendered card in the sample report with the height the page was planned from, to within 0.5 mm. Tests cover 12, 20, 21, 22 and 24 rows in both outputs, and a separate test checks that the warning banner appears for an array of 140 rows. That test checks the banner only, not the layout of such a card.

## Cable patch

Each enclosure row of each array that has rows has a Feeder and a Way, each one digit (1 to 9 and 0, listed in that order) or blank. It is notes only. Nothing counts feeders or ways, checks them, or works out a length or a load, and nothing in the rigging summary, the rigging plot or the DXF reads it. `src/engine/patch.ts` holds the digits, the colours, `fitPatch` and `trackPatches`.

The file has a `patch` list with one list per array and one `{ feeder, way }` per enclosure of that array, each value a single digit character or an empty string. The schema refuses a list of the wrong length and any value that is not one digit or blank. In a document, `Doc.patches` holds the arrays that have something set, by position in the report, like `markers`. `patchOf` pads to the enclosure count and `withPatch` sets one field. Delete and restore only change `deleted`, so the patch stays with the array.

A read-only file (approved or superseded) cannot change its patch. The dropdowns are switched off and `withPatch` returns the document as it was. This differs from the plot symbols and the print choice, which can still be changed for the session on a read-only file. Create new revision makes the file editable again.

Update from PDF keeps an array's patch row for row when the array of the same name has the same number of enclosures. When the number differs the rows cannot be matched, so that array's patch is cleared and listed in the comparison as `Cable patch`, with the number of rows that were set and the new number of enclosures. An array with no patch set is never listed.

The feeder and way columns are the last two columns of the enclosure table, on the printed card, the PDF, the image and the screen card: `#` (or `Col #` for a stack in columns, or `Row #` for a stack in rows), Type, Panflex when the report has it, Angle when it has that, then Feeder and Way. The per enclosure site angle is not on the cards, so the table has no Site column; the array's own top and bottom site stay in the facts above it, and the rigging summary, Compare and the saved file are unchanged. The columns always print. A blank cell is drawn as an empty box with a thin black outline, the size of a chip and white, so it can be filled in with a pencil, and the screen dropdown keeps its own border. `cardContent` supplies the digits, and an empty cell is a blank string and never a dash, because a dash means the report does not state the value; `patchChip` returns the empty box for it. `CARD_TABLE_WIDTHS_MM` in `card-content.ts` is the one map of column widths on the 93 mm card (`#` 6, `Col #` 12, Panflex 13, Angle 11, Feeder 12, Way 9, all in mm), and Type takes the rest, 36 mm at the narrowest. The print view lays the table out with a `colgroup` and a fixed table layout from that map, the PDF uses the same numbers, and the image scales them to its width. Type is cut with an ellipsis in the print view (CSS) and in the PDF and the image (`clipToWidth`), so a row never takes a second line and a card is as tall with a patch as without. Every value in the enclosure table and in the fixation table is centred on the cards, on the screen, in the print view, in the PDF and in the image. The exceptions are the Type column and the fixation name, which stay left.

A chip is a rectangle 3.4 mm wide and 8.4 pt high, centred in its cell, with the digit in bold 7 pt on it. The white chip has a 0.2 mm black outline, and so has the empty box of a blank cell. The chips print in colour on the pocket cards. The same colours fill the dropdowns on the screen card.

Colours follow the resistor code. The shades are chosen for a black and white print as well. Printer luma is 0.299 R + 0.587 G + 0.114 B on values of 0 to 255. Ordered from dark to light the ten chips are black, brown, blue, violet, red, green, orange, grey, yellow and white, and each step is at least 20 out of 255, so no two chips look alike on a grey print. The digit on each chip is white on the dark chips and black on the light ones, and every pair has a contrast ratio of at least 4.5 to 1 (WCAG relative luminance). `src/engine/patch.test.ts` asserts the order, the steps, the contrast, and the outline on the white chip alone.

## Images

A stacked array that has fixations shows a small block under the facts: a heading row (`Fixations`, `X (m)`, `Y (m)`, `Z (m)`) and one row for each position, with the values as the report prints them. The Z is the report's own. The ground offset is not taken off it, which matches the pickup positions in the rigging summary and the Position X, Y, Z fact. The block is one heading row and one row for each position, plus a gap, so four positions cost about five rows and a gap. A stacked card with fixations can therefore be taller than a pocket panel, and a tall stack may need a long column. A name longer than 12 characters is cut with an ellipsis on the card, in the PDF and in the image. The cut keeps it inside its column and keeps the row height. The report's own names are two letters. `layoutPocketCard`, the print stylesheet (`.pc-fix`), the image layout and the screen card all draw it from the same data.

Card content (`src/print/card-content.ts`) is plain data that both the print card and the image draw from, so they cannot disagree. `array-image.ts` turns it into a list of drawing steps (text, lines, boxes) and draws them on a canvas at twice the size. Canvas text needs no markup, so it works under the strict CSP. The layout is pure and has unit tests. Playwright checks that the download is a real PNG of the right width.

## The QR code

`src/print/qr.ts` makes the code on this device with `qrcode-generator` (MIT, no dependencies, about 20 KB) and draws it as one SVG path. The address is `APP_URL` in `src/app-info.ts`. A test decodes the picture back to the address with `jsqr`, which is a test-only dependency.

## The interface

- The page opens on a screen that explains what the app does and does not do. A PDF can be chosen or dropped anywhere on the page.
- A report with an error-level problem shows only the problem list, not the figures.
- A report with checks shows the sheet and the list of things to compare with the PDF.
- Every status has a word as well as a colour: READ OK, CHECK, ERROR, WARNING, CAUTION.
- Colours for Day and Night are tokens in `src/ui/styles.css`. `src/ui/contrast.test.ts` checks them against WCAG 2.1 AA.
- pdf.js and its worker load only when a PDF is opened, and run under the strict CSP.
- Components are tested by rendering them to HTML (`src/ui/render.test.tsx`), and the whole flow by Playwright tests.

## Not done yet

- The update prompt is not covered by an automated test, because it needs two deployed versions. It is covered by hand before a release.
- The sample fly sheet's Btm Height + 1 row is deliberately left out.
- Folding sheets are out of scope. Cabling is limited to the cable patch on the cards: a feeder and a way digit for each enclosure, typed by the person, with no lengths, loads, counts or checks. Cabling sheets from other tools are out of scope.
- Only Soundvision is supported. Other tools would need their own reader.
